# execute — 계획에서 구현까지

입력: `docs/plans/active/ep-*.md` 하나.

## 가드

- ep가 없으면: 절차 1단계나 `plan` 스킬을 가리키고 멈춘다.
- 레이블 확인: `[Draft]` → 진행(승인 필요) ·
  `[Approved]` → 진행 · `[In Progress]` → 이전 세션이 중단된 것이다.
  `[Draft]`로 되돌리고 왜인지 Change Log 1줄을 남긴 뒤 다시 시작 ·
  `[Done]` → 끝난 계획은 다시 돌리지 않는다. 멈춘다.
- Affected Files가 걸친 폴더의 AGENTS.md를 읽는다. 파일이 없거나 `## 명령어`가
  비어 있으면 **추측해서 실행하지 않는다** — `setup`을 요청하거나 사람에게
  확인받아 그 폴더 AGENTS.md에 기록한 뒤 진행한다.

## 1. 조사 (읽기 전용)

Affected File마다: 파일을 읽고 → 1홉 import 의존을 확인하고 → 그 테스트를 찾는다.
위험 신호(전역 상태 · 공개 API 변경 · 마이그레이션 · 인증/보안)가 있으면 ep에
`## Risk`를 채우고 이유를 적는다. 계획에 없던 파일이 필요해지면 이유와 함께
Affected Files에 추가한다 — 승인은 다음 단계에서 한 번에 받는다.

## 2. 순서

ep의 `## Implementation Order`를 채운다 — 항목마다
`{n}. {경로} {CREATE|MODIFY|DELETE} — {왜, 한 줄}`.
빠진 파일이 없는지 기준과 교차 확인한다.

## 3. 승인

AGENTS.md `작업 절차` 2단계대로 계획 경로·파일·기준을 제시하고 기다린다 —
기다리는 동안 도구를 부르지 않는다. Risk가 있으면 요약에 포함한다.
승인되면 합의된 파일과 기준을 옮겨 적어 `## Approval`에 덧붙이고 Status를
`[Approved]`로 바꾼다.

## 4. 구현

Implementation Order 순서대로, 항목마다:

- **tdd 규율 아래** (RED→GREEN — `.agents/skills/tdd/SKILL.md`)
- 첫 소스 변경 직전에 Status를 `[In Progress]`로 바꾼다
- 변경마다 ep `## Change Log` 1줄을 **즉시** (절차 3단계)
- 승인된 파일만 건드린다 — 실패를 계획 밖 파일로 보상하지 않는다. 다른 파일이
  필요하면 추가하고 재승인부터 받는다.

명령어가 `(미검증)`이었다면 첫 RED 실행이 곧 검증이다 — 제대로 돌면 그 폴더
AGENTS.md에서 표시를 지우고, 안 돌면 멈추고 사람에게 확인받는다.

## 5. 검증

걸친 폴더 전부의 `## 명령어`로 빌드와 테스트를 돌리고, 결과를 손대지 않고 읽는다.

red이면:

- 원인이 분명하면 → 같은 ep 안에서 고치고(Change Log 1줄) 다시 돌린다
- 원인을 모르면 → `debug`의 추적 루프로 근본 원인을 확인한 뒤 같은 ep 안에서 고친다
- 같은 실패를 3번 못 고치면 → 멈추고, red 그대로 가설 기록과 함께 사람에게 보고한다

**승인된 기준과 기존 테스트는 green을 만들려고 고치지 않는다. 고쳐야 한다면
그것은 재승인 대상이다.**

green이면 기준마다 확인 근거를 `## Acceptance Criteria` 같은 줄에 적고 체크한다
— 테스트 경로 또는 `수동 확인: {방법}`.

Risk가 있거나 파일을 4개 이상 고쳤으면 독립 리뷰를 권한다 — **새 세션에서,
되도록 구현자와 다른 모델로** `review ep-{slug}`.

## 6. 완료

사람 `lgtm` → 절차 5단계 (Run History 1줄 → Status `[Done]` → `done/`으로 이동
→ 커밋). Run History 줄에 검증 결과를 함께 적는다.

**끝났다고 볼 때:** 단계마다의 산출물이 ep에 있고, 중단·실패를 포함해 Run History
1줄이 있다. 기록 없는 실행은 하지 않은 실행이다.
