# tdd — red → green 루프

구현은 이 루프의 반복이다. 리팩터링은 루프 밖 — 전체 green 이후에만 한다.

## 루프

1. **RED:** 실패하는 테스트를 하나 작성하고 **실행해서 실패를 확인**한다.
   실패를 본 적 없는 테스트는 신뢰할 수 없다.
2. **GREEN:** 그 테스트를 통과시키는 최소 구현만 작성한다. 다음 테스트를
   예상한 선반영 없이, 지금의 red를 green으로 만드는 것까지만.
3. 반복 — 한 번에 한 slice: 테스트 하나 → 구현 하나.

## seam — 테스트를 어디에 쓰나

테스트는 공개 인터페이스(**seam**)에서만 쓴다. 시작 전에 ep의 인수 기준과
대조해 이번 작업의 seam 목록을 정하고, 목록 밖 내부 구현에는 테스트를 쓰지
않는다. 인수 기준 1개당 최소 1개의 테스트가 seam 위에 있어야 한다.

## 안티패턴 (의심되면 [anti-patterns.md](./anti-patterns.md)의 예시와 대조)

- **구현 결합** — 내부 협력자를 모킹하거나 비공개 함수를 검사한다.
  판별법: 동작이 같은데 리팩터링만으로 테스트가 깨지면 이것이다.
- **동어반복** — 기대값을 코드와 같은 방식으로 재계산한다
  (`expect(add(a,b)).toBe(a+b)`). 기대값은 독립 출처(스펙의 구체 숫자,
  손으로 푼 예제)에서 가져온다.
- **수평 슬라이싱** — 테스트를 전부 먼저 쓰고 구현을 전부 나중에 한다.
  상상한 동작을 검증하게 된다. 항상 수직으로 — 한 slice씩.

**완료 기준:** 모든 인수 기준에 대응 테스트 존재 · 전체 테스트 green ·
변경마다 ep Change Log 1줄 (AGENTS.md 계약 §증거 형식).
